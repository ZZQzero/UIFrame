# 照片备份 v2 实施后逐项审查

日期：2026-10-02。范围为 [实施计划](GalleryBackgroundProtocolPlan.md) 的 39 条阶段清单、B01–B24 故障矩阵，以及对应源码、测试和构建产物。不是整个 UIFrame 包的所有功能审查。

后续完整源码复查的F1–F6已修复并重新验证，见 [GalleryBackgroundFullReview.md](GalleryBackgroundFullReview.md#6-修复结果与最终验证)。当前结果以该报告及执行记录为准，下文保留本次审查当时的证据。iOS保留系统后台传输，协议已改为可信最终终点及服务/网关不得重定向；最终URL/可用metrics检查只能事后检测，不能由旧的构建证据推断具备跳转前拦截能力。

结论：本轮发现的五类实现问题已修正并重新验证受影响路径。阶段清单保持 **31 项完成、8 项未验收**；未完成项集中在旧版同条件基线、手机系统行为、长期负载及发布验收。不能将“功能已编写、构建通过”解释为商业发布验收全部通过。

## 1. 审查发现与处理

### R1：显式核对丢失取消意图，且能过早替换在用凭据

- 原路径：取消请求失败后，公开 `ReconcileTaskAsync` 传入 cancel=false；共享仓库将 desired_action 从 2 改成 0，下一次创建的是 Query，可能重新得到上传授权并恢复上传。
- 复现：真实发布库得到 `beforeDesired=2, afterDesired=0, nextKind=1`。另验证旧 API 凭据尚未释放时也能成功替换引用，造成所有权不一致。
- 修正：`ProtocolReconcile` 保留已有取消意图，要求前次上传、控制请求、上传描述和 API 凭据均实际释放后再接收新凭据。规则在共享仓库内统一执行，没有给 C# 添加补救分支。
- 验证：原生旧实现的取消意图、提前核对测试均失败，修正后通过；Unity 新增 `ReconcileRetainsFailedCancellationAndDoesNotResumeUpload`，公开 API 继续 Cancel 仲裁、没有第二次 PUT，测试通过。普通未知上传的显式核对仍通过。

### R2：运行中的移动执行器漏记后续照片的系统受理

- Android 原路径：已有 Run 时只 signal 后返回，后续交接项的 system_scheduled 仍为 0，Submit 最后的受理检查错误地报告失败。
- 复现：生产 Java/JNI/发布仓库中，Automatic 和 UserInitiated 两种模式的新项均为 `system_scheduled=false`。
- 修正：活动执行器接收新增工作时持久记录受理；已进入停止阶段则明确拒绝。用同一唤醒标志关联接收、等待和空闲退出，避免接收成功后丢掉唤醒。
- iOS 同类路径：已有控制请求或上传配额占满时不一定创建新系统任务。已受理的 URLSession 任务及其完成回调负责推进后续工作，也必须记录本次受理；没有系统任务时不能凭等待集合伪造受理。
- 验证：Android 增补运行中接收、停止时拒绝、不重复提交 Job 的宿主回归并通过。iOS 完成源码路径核对及设备目标 Release 编译链接，尚无系统运行证据。

### R3：过期上传描述释放后，需要额外一次驱动才能重新登记

- 原路径：平台先执行 ProtocolActions，再释放过期描述；阶段仍为 FileTransfer，当前回调后不能创建 Plan，也没有下一检查时点。iOS 缺少后续系统事件时可能停住；桌面和 Android 也会增加等待。
- 复现：真实库按该顺序执行后 `phaseAfterRelease=1, controlAfterRelease=null, next_utc=null`。
- 修正：描述实际释放和阶段切回 Plan 在同一次仓库提交内完成，删除依赖第二次 ProtocolActions 扫描的转换。
- 验证：加强授权到期测试，释放后立即创建 Plan；原实现失败、修正后通过。暂停、取消、过期认领竞态与实际释放前禁止清理的相关回归均通过。

### R4：慢速重复 PUT 阻塞已到达文件的核验和清理

- 原路径：整个网络接收期间占用上传尝试锁；服务唯一确认线程等待该锁，其他独立 ready 文件也无法确认。
- 复现：两份文件已到达，第一份启动慢速重复 PUT 后，confirm_pending 被阻塞，第二份也没有回执。
- 修正：每个 incoming 文件由独立请求持有；writing 记录保护活跃文件。仅登记和发布持有短锁，网络读取不持锁。过期维护在同一锁序中检查 writing 记录，新增按上传尝试查询的索引。发布再次检查取消和拒绝状态。
- 验证：受控慢请求尚未结束时，两份已到达文件均确认、清理，正在写入的文件保留；请求结束后正常核验和清理。维护不能关闭正在写入的尝试，取消仍获正确仲裁。服务完整 33 项通过。

### R5：iOS 自主回调始终跳过 Plan 聚合窗口

- 源码检查：ControlCreate 的 flush 参数原来固定为 YES，后台回调无法使用共享仓库的 250ms Plan 聚合规则。
- 修正：自主回调遵守聚合窗口；显式 wake 在返回 Submit 前提交尾批。已有有限后台断言负责聚合收尾，没有引入新计时状态机或延长常驻时间。
- 验证：共享聚合、未来 Query 不挡 Plan、暂停保留时点的测试通过；iOS 适配完成编译链接。实际 URLSession 延期和后台断言时序仍属于 P5 真机验收，不能以编译结果替代。

另外修正了证据表述：Android 宿主夹具运行的是生产调度/绑定/清理代码及真实 JNI 仓库，Context、JobScheduler 等由替身提供；没有在宿主执行完整 Java HTTP Plan→PUT→Query 链路。B17 的“无 C# 后台完整链路”仍未验收。
