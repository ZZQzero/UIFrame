# 长期照片备份与图库性能实施计划

日期：2026-09-30
状态：复审缺陷已修复，设备与商业发布验收未完成（2026-10-01更新）。共享 BackupRepository、图库索引、缩略图缓存、批量操作、清理及服务器 TTL 均已实现；当前运行接口见 Gallery.md。桌面行为、进程中断和移动端发布构建已有证据，真机及长期压力门槛仍未通过。
适用范围：UIFrame / Unity 6000，Android、iOS，以及现有桌面目录与 Editor 验证路径。

本文落实 SQLite、图库增量刷新、缩略图缓存、批量任务管理和清理策略。基础能力与现有接口见 [Gallery.md](Gallery.md)，已执行验证见 [GalleryValidation.md](GalleryValidation.md)，早期总体方案见 [GalleryImplementationPlan.md](GalleryImplementationPlan.md)。本轮相关存储、并发和生命周期决策以本文为准。

通用数据库能力单独落在 Runtime/Sqlite，见 [Sqlite 模块说明](../Runtime/Sqlite/README.md)和[实施计划](../Runtime/Sqlite/ImplementationPlan.md)。连接、事务、查询、取消与快照由通用模块负责，本文只定义图库与照片备份的业务存储；游戏存档等其他业务可以独立使用同一模块。

执行记录（2026-10-01）：通用核心使用 ABI 3，业务仓库使用 ABI 1；C#、Android、iOS 已接入同一份原生业务状态机。四目标产物可复现构建，照片任务 / 策略 / 基线 / 回执的 JSON 持久化及全量 GetTasks 已移除。构建和桌面测试不能代替下列阶段的真机与长时门槛。

## 1. 成功标准与范围

完成后应满足：

1. 历史任务和照片版本增长时，启动、显示一页任务和检查一页照片均不加载全部历史记录。
2. 照片新增、编辑和可见范围变化能够驱动局部更新；无法取得可靠增量时，明确进行完整元数据核对。
3. 相同照片版本、相同显示参数复用缩略图；重复在途请求只执行一次处理，使用者独立释放。
4. 支持任务分页、汇总、变化通知，以及选定任务或筛选结果的批量控制。
5. 清理能够释放可回收资源，同时保留恢复任务、判断已经备份和排除历史照片所必需的记录。
6. 崩溃、磁盘错误、权限变化和原生迟到回调均不能造成假成功、重复认领或提前删除在用文件。

本轮不增加自动删除手机原图、双向删除同步、后台持续发现新照片、视频、Live Photo / RAW 成套备份、云端图库恢复界面和新的图片编辑功能。后台上传继续由系统调度；新增监听不构成后台常驻承诺。

按已确认要求，直接替换持久化实现：不增加旧 JSON 的识别、读取、导入、迁移或双写代码，也不保留第二种任务存储后端。HTTP 和桥接消息仍可使用 JSON。当前格式的异常退出恢复属于必要功能。

## 2. 实施前基线（历史对照）

| 模块 | 实施前实现 | 本轮解决的问题 |
| --- | --- | --- |
| ImageBackupService | 任务逐文件 JSON，启动加载全部任务；扫描基线与回执读取到字典 | 文件数量、启动读取、历史常驻内存、全量快照 |
| AutomaticImageBackup | 周期性分页遍历来源，按来源版本记录跳过已处理项 | 每轮仍枚举整个范围，没有系统变化监听 |
| GameGallery / GameImageDirectory | 全量快照接口与逐页消费接口并存 | 缺少持久元数据索引及变化游标 |
| GameImageReader | 预览和转码共用一个处理槽位；每次请求创建新纹理 | 缺少共享缓存及相同请求合并 |
| 任务控制 | 队列暂停 / 恢复、单任务重试 / 取消、清理失败重试 | 缺少批量操作、分页任务中心和历史保留规则 |
| Android / iOS 后台 | 原生独立保存执行记录，C# 持久交接并对账 | 数据库化时必须延续执行代次、释放确认及故障语义 |
| 本机服务器 | SQLite 元数据、文件存储、校验与幂等提交 | 未完成上传会话缺少自动过期回收 |

现有图片暂存预算默认 512 MiB，只覆盖备份准备文件，不是整个模块或进程的空间上限。现有单图像素限制、默认不可读纹理、无 mipmap 和串行图片处理均继续作为本轮设计约束。

## 3. 固定的架构决策

### 3.1 数据库职责与写入所有者

按商业游戏的长期维护要求，统一 Runtime/Sqlite 的原生存储核心，并按业务生命周期划分两类数据。每类数据只有一个业务仓库所有者，Android、iOS 与 C# 不各自实现 SQL 或独立改写同一任务状态：

| 数据库 | 内容 | 唯一业务写入者 |
| --- | --- | --- |
| library.sqlite，应用图库索引一份 | 照片元数据、图库查询范围、授权代次、索引核对记录和图库变化序号 | C# 图库仓库，通过 UIFrame.Sqlite 提交到统一核心 |
| catalog.sqlite，每个服务器 / 账号仓库一份 | 备份范围、基线、发现处置、任务、执行代次与系统关联、确认回执、文件释放、批量操作、清理意图及策略 | 一份跨平台共享的原生 BackupRepository，通过统一核心执行 |

library 可由普通图库界面独立打开，不要求账号、服务器或启用备份。catalog 是备份任务与执行结果的唯一事实来源，执行记录放在其中的 task_attempts 表。C# 备份服务、Android 和 iOS 都调用同一个 BackupRepository 命令接口；C# 不绕过它打开 catalog，平台调度代码不自行保存另一套任务状态。

BackupRepository 属于照片业务模块，其 SQL、schema 和状态转换只有一份 C/C++ 源码，各平台与桌面测试编译同一实现；它依赖通用存储核心，不把备份规则塞进 Runtime/Sqlite。iOS 在没有 C# 服务时接收回调，也能通过该仓库在一次事务中提交执行结果、确认回执和清理意图，无需等待 C# 再进行第二次状态提交。

图库与备份之间仍不使用跨库事务：图库变更由 BackupRepository 与消费位置一起提交为发现记录。消费位置包含 library 身份、索引代次、范围修订号和日志序号，不是孤立整数。每页校验连续性，只提交该页实际处理到的序号；索引重新建立、范围改变或日志截断后明确核对对应范围，不能把新索引的相同序号当作旧进度。C# 扫描、文件准备、网络请求与系统调度仍各有执行责任，但所有备份事实通过仓库命令写入。

完整核对开始时记录索引代次和日志起点，完成枚举后继续处理该起点之后的变化；激活消费位置前再次检查连续性。期间日志被截断或权限代次变化，核对保持未完成并报告 RequiresReconcile，不能以扫描结束时的最新序号直接跳过变化。已持久发现通过唯一键消重，重新核对不重放失败上传。失联消费者不能无限阻止日志保留策略。

同一文件只对应一个核心数据库上下文。图库索引由应用服务拥有，备份仓库由可脱离 Unity 运行的原生服务拥有；关闭 C# 门面只解除客户端连接，不关闭仍有后台任务的仓库。核心统一管理串行写入、短只读查询、配额与工作线程，事务中不等待外部操作。单任务失败不影响无关任务；仓库故障只停止依赖它的工作。

原生启动定位必须在 L0 验证：平台可在 Unity 启动前定位模块私有根目录，系统任务保存仓库 ID、任务 ID 和代次，仓库 ID 映射到约定的私有子目录。恢复只打开已存在的 catalog，不因路径丢失创建空库。目录策略与首次创建由业务工厂固定，不能依赖 C# 静态变量或只存在内存中的注册表。

### 3.2 SQLite 接入

- C# 图库仓库使用独立 UIFrame.Sqlite 程序集；原生 BackupRepository 使用同一核心的受控事务接口。两者不复制通用连接、工作队列或事务封装。照片模块负责在 Unity 对象操作前切回主线程。
- 通用模块 S0 锁定 SQLite 官方源码、版本、编译配置与稳定 C ABI。C# 门面、原生备份仓库和平台适配共同依赖该产物，不再分别采用不同数据库封装来保存备份数据。
- Android / iOS 只适配系统调度、网络、权限和凭据；SQL、任务状态转换、幂等与文件释放判断统一在 BackupRepository。桌面原生测试同样编译该仓库，不能用另写的 C# 状态机替代验证。
- L0 验证引擎符号隔离、实际加载版本、Android ABI、IL2CPP/AOT 和代码裁剪，以及备份模块没有再次嵌入 SQLite。构建不通过时修正唯一方案，不在运行时自动切换后端。
- iOS 数据库及 WAL / SHM 目录需要验证锁屏后的文件保护行为。首次解锁前不可访问与数据库损坏分开报告；不为后台读写取消账号凭据的安全存储。
- 开启外键、WAL、可靠提交设置；关键持久状态使用 synchronous=FULL，并验证平台实际设置。WAL 提升读写协作，不提供多写入者同时提交。
- 连接、语句、事务和取消均由统一核心管理；采用固定连接数、线程池、参数 / 结果预算、页缓存目标和锁等待期限。错误向调用方传播，不无限等待或循环重试；原生任务回调的持久提交不依赖 C# 完成泵。
- SQL 提交成功后才发布新的内存状态和变化通知。提交结果不明时先停止相关仓库，不能按失败假设删除可能已经提交的数据文件。
- 初始化只接受本轮唯一 schema。校验数据库标识、账号、服务器及 schema 版本；无效或损坏时明确失败，不删除重建。版本校验不是旧 JSON 检测。
- 每次删除记录不执行 VACUUM。在空闲机会执行非阻塞 checkpoint 并测量持续时间；不假定 SQLite 提供任意页数的 checkpoint 时间片。压缩数据库须单独计算时间、额外磁盘需求和锁占用。

### 3.3 数据与文件边界

照片、上传暂存文件和可选预览文件放在文件系统；数据库记录路径、大小、哈希、状态和归属，不存整张图片 BLOB。路径必须位于模块持有的目录内，不通过外部输入拼接越界清理目标。

数据库事务不能覆盖文件创建、删除或系统任务调度。因此任务文件采用“准备中 → 持久接收 → 使用中 → 待清理 → 已清理”的归属记录；启动恢复只根据当前记录与实际资源核对，不猜测或重建丢失的备份事实。

## 4. 最小数据模型与查询规则

以下是职责表，不要求每个职责生成一个公共类；L0 固定具体 SQL 和约束。assets、scope_assets、library_scopes 及图库核对记录属于 library，其余备份数据属于 catalog；各库的扫描记录和变化日志遵守同一消费契约。跨库只引用稳定来源身份，不建立跨库外键或跨库事务。

| 数据 | 最少记录内容 | 必要约束 / 索引 |
| --- | --- | --- |
| store_settings | 仓库 ID、服务器、账号、队列暂停、持久策略 | 单仓库身份不可替换 |
| scopes | 来源、授权目录标识、相册、递归配置、是否包含历史、权限代次、初始化状态、平台游标 | 稳定范围 ID；不能只以显示名识别 |
| library_scopes | 图库查询范围、实际授权范围、索引代次和平台核对游标 | 可独立于备份配置存在 |
| assets / scope_assets | 来源身份、内容版本、名称、尺寸、修改信息、范围成员关系、可访问状态 | 来源身份唯一；按范围、排序键及资产 ID 分页 |
| scan_runs / scan_items | 核对代次、权限 / 范围修订号、日志起点、已见版本、初始化基线暂存项和完成标记 | 分页落库；按范围 + 代次 + 来源 + 版本查询；完整基线通过激活记录生效，不在最后复制全部行 |
| discoveries | 范围、来源、版本、排除 / 待准备 / 已接收 / 准备失败 / 明确取消等处置 | 范围 + 来源 + 版本唯一；失败版本只按显式策略再处理 |
| backup_receipts | 来源版本、已确认备份 ID、哈希、字节数、名称 / MIME、确认时间 | 独立于任务历史；仅服务端确认后记为已备份；可用于下载验证 |
| tasks | 稳定序号、任务 / 批次 ID、来源版本、状态、期望操作、文件、会话、代次、错误、时间 | 状态 + 调度时间 + ID；创建序号 + ID；来源 + 版本 |
| task_attempts | 仓库 / 任务 / 执行代次、系统任务标识、提交意图、实际执行结果、服务器结果确定性、文件释放与凭据释放状态 | 任务 + 代次唯一；旧代次不能更新新代次的业务结果 |
| operations / operation_items | 批量操作 ID、参数指纹、动作、筛选 / 显式 ID、创建序号上界、选择游标、阶段、目标集和结果 | 操作 ID 唯一，同 ID 不同参数拒绝；目标分页构建，执行阶段固定；操作头与可过期的逐项结果分离 |
| file_records | 文件归属、实际大小、准备 / 已移交 / 待清理状态、清理错误 | 按状态和时间查询；在用文件不能成为清理候选 |
| change_log | 仓库身份 / 索引代次、递增序号、对象、动作及版本；持久消费者位置 | 按序号读取；每页验证游标，截断或换代后明确失效 |

“扫描见过”“准备失败”“用户取消”和“服务器已确认备份”必须分别表达。清理任务历史后仍能阻止已备份、排除历史或明确取消的相同版本被自动重新入队。手动再次备份属于显式新请求。

现有 DownloadAndVerifyAsync 通过任务 ID 读取备份信息。本轮清理任务历史前，必须提供基于持久备份回执的下载入口，并更新调用点；否则删除任务会同时丢失下载定位和校验依据。此项只解耦现有下载能力，不扩展为云端图库浏览产品。

来源版本用于发现变化，SHA-256 用于确认暂存内容；二者不能互相替代。缓存键、图库索引和自动发现共用来源身份 / 版本模型。相册移动、名称变化、授权代次和内容变化分别记录，避免仅因界面元数据更新就重新上传像素未变的照片。

平台只报告“可能修改”时应标记内容待核对，不能猜测没有变化。准备文件前后核对可取得的来源版本；若已变化，不将复制出的字节登记为旧版本的确认备份，保存可观察的来源变化结果并让新版本独立参与发现。

查询固定规则：

1. 默认按稳定创建序号 / ID 做任务游标分页，每页最多 200 项；不使用随页数增长的大 OFFSET，不开放每帧全量 GetTasks 调用路径。
2. 游标绑定仓库、筛选条件、排序和查询上界。任务状态为实时值，变化通知提示刷新；不将跨页结果宣称为一个长期冻结快照。
3. 批量操作先持久保存筛选条件和创建序号上界，再以稳定键分页登记目标与选择进度，选择结束后固定集合并执行；后来新增的任务不加入该批。筛选中可变状态的含义见 5.4，不用一次大型 INSERT SELECT 或长读事务实现点击瞬间的全库快照。
4. 自动发现以一页来源批量查询已处理版本，避免逐张打开连接和执行独立查询。
5. 高频状态汇总使用按状态维护的计数或经测量可接受的索引查询；任务中心不靠加载全部记录后计数。
6. 业务仓库仅缓存有界的活跃任务、页面和语句；不在 SQLite 外再维护全部任务 / 照片 / 回执字典。
7. 变化日志超过保留窗口后，临时界面订阅得到 RequiresRefresh。自动备份的未消费发现持久保存在 discoveries，不依赖无限增长的通知日志。

## 5. 关键流程

### 5.1 接收、交接、完成

1. C# 调用 BackupRepository 登记带 OperationId 的准备操作，逐文件准备并流式计算哈希；文件刷盘、落到最终私有位置后，调用 Accept，在一个 catalog 事务中提交本批任务及文件归属。本批项数、字节和实际 SQL 数受预算约束；大量照片分批接收，不能承诺跨批原子成功，也不能用“200 项”替代通用模块“200 条 SQL”的计算。提交前确定失败才清理未移交文件；提交结果不明时保留文件并按 OperationId 核对。
2. 自动发现通过同一仓库命令保存候选元数据，受暂存容量约束逐项准备；空间不足保留待准备候选，不提前复制整库原图。
3. 准备传输时，BackupRepository 在 catalog 中保存任务提交意图、执行代次、不可变文件和会话身份；平台执行器在事务之外创建 / 唤醒系统任务。
4. 平台报告系统任务关联。相同“仓库 ID + 任务 ID + 代次”的重复事件由仓库幂等处理；参数不一致明确失败。恢复时查询系统任务并核对关联，不能仅凭提交调用没有应答就再次创建传输。
5. 上传或系统回调将结果交给共享仓库；它在一个事务中校验代次、保存执行结果、确认备份回执、任务状态和清理意图。iOS 后台事件在仓库处理结束后释放系统 completion handler，不等待 Unity 启动；处理失败同样必须收尾，释放系统回调不表示备份成功。
6. 平台分别报告传输文件和凭据实际释放。仓库只有确认所有使用者释放后才允许清理；文件删除等外部副作用通过持久意图与完成记录恢复。C# 读取已提交变化用于显示和后续发现，不再次裁决同一完成状态。

崩溃窗口逐项验证：文件落盘后 catalog 未提交、提交结果交付前进程退出、catalog 已保存意图但系统任务尚未创建、系统已接收但关联未保存、服务器已提交但响应丢失、结果已提交但系统回调确认丢失、文件已删除但清理记录未提交。

网络 / 系统调用不持有数据库事务。未知服务器提交结果保留会话与幂等身份并通过现有协议核对，不生成新身份猜测重传。

回调持久提交失败或文件保护暂时不可访问时，报告故障并停止受影响仓库的后续调度，不能无限扣留系统回调等待数据库恢复。恢复入口根据此前持久化的提交意图、系统任务和服务器幂等结果核对；不能假设系统必定再次投递同一回调。不可中断的数据库 I/O 若超出系统可用时间，按未确认结果处理并保留文件，不能为了及时释放回调提前发布成功。该失败路径须在无 Unity 环境验证。

暂停、取消、恢复和系统完成事件都通过同一仓库串行裁决。完成先提交后到达的取消不能改写已确认备份；停止成功与服务器是否已提交分别记录。旧代次迟到回调只完成旧资源的实际释放，不影响新代次。该仓库契约在三端共用相同测试向量。

桌面和前台托管 HTTP 上传同样从共享仓库取得执行代次与文件使用资格，通过同一结果命令交付完成 / 释放；只替换传输执行方式，不保留第二套 C# 任务状态机。Android / iOS 后台执行不依赖 C# 的结果消费速度来确认持久成功。

### 5.2 图库增量刷新

| 来源 | 变化触发 | 增量能力与完整核对条件 |
| --- | --- | --- |
| iOS PhotoKit | PHPhotoLibraryChangeObserver，维护对应 fetch result | 有增量信息时处理增删改；无增量详情、重开、权限变化时核对可见范围 |
| Android MediaStore | ContentObserver | 支持的版本使用卷标识、MediaStore 版本与 generation；删除、未知 URI、重启后无法连续衔接时核对 ID 集合 |
| 普通目录 | 支持平台上的 FileSystemWatcher | 通知作为变化提示；缓冲溢出、重开或能力不支持时采用声明过的元数据核对 |
| SAF / 授权目录 | 提供者明确支持的通知能力 | 第一版按提供者能力报告；通用方案为恢复前台和配置周期的元数据核对，不宣称实时监听 |

处理顺序：

1. 先订阅变化，再开始初始查询；扫描期间保存“需要再核对”的标记和有界变化集合，避免查询 / 订阅间隙漏项。
2. 短时连续通知合并，默认 300 ms 安静窗口，连续通知时最多等待 2 s 发起下一轮。执行中的核对不并发重入，新事件交给后续一轮。
3. 通知集合达到配置上限后记录 RequiresReconcile，不能丢弃事件并宣称已经同步。上限保护通知内存，完整核对负责补齐。
4. 原生逐页读取元数据，library 分页更新。完整枚举成功且权限 / 范围修订号仍一致后，才进入缺失成员处理阶段；按稳定键分批标记，仅处理本轮未见且之后没有被新事件更新的成员，全部处理完成才推进完整核对游标。失败不把未读到的照片标成删除；中断的后处理保留进度。catalog 按页消费已提交的变更，并在同一个本地事务里保存发现记录及消费位置。
5. 每轮读取前记录平台上界，完成后验证平台数据版本；只推进已处理的游标。扫描期间变化保留下一轮资格，不用结束时的最新值直接跳过它们。
6. 提交后发布 Added / ContentChanged / MetadataChanged / RemovedFromScope / AccessChanged。缩略图按内容版本失效，备份按来源版本生成候选，界面更新受影响项目及相册计数。
7. 恢复前台、重新启动、游标过期或索引代次变化时核对连续性。系统通知只提供执行机会，不能替代持久发现记录。

首次排除历史照片时，将本次完整基线实际包含的来源版本按代次分批写入暂存集合；完成枚举并校验范围 / 权限及日志连续性后，用一个短事务激活该基线与范围。判重查询通过激活代次将这些项视为 Excluded，不在最后把整库版本逐条复制到 discoveries。未激活集合没有排除效力，中断保留未完成状态；废弃代次按页清理。

初始化期间的通知必须继续核对；未包含在基线中的新增版本仍可入队。此语义以完整基线集合为准，不宣称精确对应按钮点击时刻，更不能只比较拍摄时间。缺失成员处理与基线启用都不要求十万行单事务，不能通过提高通用事务超时掩盖长时间占用写连接。

权限缩小、相册移出和真实删除是不同原因；不能从“当前看不到”推断全库删除。权限变化时暂停相关自动发现及未完成传输并重新确认范围。此过程不删除服务器备份，也不自动弹出权限窗口。

现有移动端枚举会先生成整库分页临时文件。L3 同时改进该路径：Android 消费有界 Cursor 页；iOS 分批读取 fetch result 属性。系统自身可能持有集合，但桥接层不先序列化整库或积累全量 JSON。不支持直接分页的提供者只承诺逐页交付及明确的内部成本。

### 5.3 缩略图缓存

- 新增应用级 ImageThumbnailCache，业务显式创建和关闭；普通直接读取接口仍可用于无需共享的独立预览。
- 将 ImageTexture 的内部所有权统一为租约。每个使用者持有独立句柄；底层 Texture / Sprite 只由资源所有者释放，业务不得直接 Destroy。直接加载持有独占租约，缓存命中发放共享租约。
- 缓存键包含来源身份、内容版本、目标尺寸、像素限制、Readable 及实际影响输出的变换参数。同照片不同尺寸不混用。
- 同键在途请求共用一次加载；每个等待者可以单独取消。全部等待者取消时请求停止，无法立即停止的解码完成后取得资源并释放，不遗留纹理或悬挂等待。
- 在途项持有自己的来源读取租约，不借用第一个调用者即将释放的句柄。最后等待者离开或条目失效时，先将该加载从可复用映射摘除再取消；相同键的后续请求取得新加载代次。旧加载完成时只能完成自身等待者并释放自身资源，不能移除或覆盖新条目。
- 内容变化时旧条目停止接受新租约；已有使用者可完成本次显示，最后释放后销毁。旧请求迟到返回不得占据新版本键，列表重绑也不能被旧结果覆盖。
- 初始空闲缓存预算 32 MiB，按纹理实际格式、尺寸及 CPU 副本估算字节并以 Profiler 校核；LRU 仅淘汰无人使用的资源。正在显示的资源、在途处理及待 Unity 销毁的资源分别计量。
- 单条结果大于缓存预算时可作为有效在用租约返回，释放后立即回收，并报告未保留缓存；不把图片缩小到调用者未要求的尺寸。
- 维持现有图片处理并发 1，不因加入缓存提高解码并发。处理队列优先可见请求；本轮不开启自动预取，避免增加未经测量的工作集。
- 统一图片处理入口限制待处理不同键数量、等待者总量及元数据字节；共享缓存与独立预览共用该准入，不在缓存外另开无界等待队列。候选默认上限为 128 个不同键、512 个等待者、1 MiB 请求元数据，L4 按真机校准。复制请求或保留来源之前检查配额；超限请求明确失败，已受理请求仍有终态。合并同键不重复占解码槽，但仍计入等待者预算；取消与完成及时归还额度。
- 缓存关闭后拒绝新请求、取消未完成加载并释放空闲条目；已交付租约仍可正常释放。全局关闭不能销毁 UI 仍持有的纹理。
- 文件的修改时间 + 大小不足以证明所有内容变化。监听失效、来源版本未知或业务原地修改时必须增加内容修订号或显式失效；不能用只有路径的长期缓存。

第一版只交付内存共享缓存。跨启动磁盘缩略图缓存留作后续可选项，不为本轮预建文件索引与持久化分支。

32 MiB 是空闲复用预算，不包含已交付租约。列表必须虚拟化，并在单元离屏或换图时释放租约；缓存不能代替业务释放屏幕外对象。验收同时覆盖快速取消 / 重绑造成的请求积压，以及 Unity 延迟 Destroy 造成的短期峰值，不能只看稳定后空闲缓存。

### 5.4 批量任务管理

公开区分整个队列暂停、选定任务暂停及网络策略等待。全局暂停优先；恢复选定任务不能解除全局暂停，已完成任务不能被恢复成待上传。

提交命令在短事务中保存 OperationId、参数和创建序号上界后返回，状态为 Selecting；按页固定目标后进入 Running，最后进入终态。每页目标登记和选择游标在同一事务提交，选择阶段不执行动作。崩溃恢复从持久进度继续未失败工作，已记录失败的阶段不自动重跑；选择失败时已登记项保持 NotExecuted。

command.OperationId 在提交前由调用方确定并保存。相同 ID、相同参数返回原操作，参数不同则拒绝；提交结果未知时先按这个 ID 核对，不能另造 ID 重复发送。操作头保存最小参数指纹、终态及汇总，逐项结果过期不删除该幂等依据；无需另建一套业务回执状态机。

显式 ID 列表表示调用方选中的身份集合，遵守命令参数预算；筛选命令仅考察提交上界以内的任务，可变筛选条件按该页读取时的状态判断。界面说明是“逐步匹配并处理”，不声称冻结了点击瞬间所有任务的状态。Running 阶段集合不再增加，执行前仍检查合法状态，变化后不适用的项目报告 NotApplicable。这样只需统一的分页和仓库状态机，无需长期持有数据库快照或保存全部历史状态。

operation_items 保存任务身份与必要结果摘要，不通过外键级联随任务历史一起删除，也不因待处理意图永久保留原任务。历史清理仍按实际执行、对账与文件归属判断资格；目标已被合法清理时，后续命令报告 NotApplicable / 任务不存在，清历史命令可报告 AlreadySatisfied。选择期间被清理的任务不再参与后续页匹配，不能为了固定候选而封锁整个范围的清理。逐项结果至少包含 Applied、AlreadySatisfied、NotApplicable、Failed、Pending / NotExecuted 及原因；QueryOperationAsync 同时返回选择进度，目标数量在选择结束前不是最终总数。

命令受理、目标选择完成与“执行者确已停止并释放资源”分别是三个确定点。取消等待不等于取消这项持久操作。

| 操作 | 完成条件 |
| --- | --- |
| Pause | 意图持久化，对应执行者停止并确认释放；保留继续所需数据 |
| Resume | 合法暂停任务恢复调度资格；实际执行仍遵守全局暂停与网络策略 |
| Retry | 对应失败任务获得新尝试资格，旧代次已释放；不自动扩大到其他任务 |
| Cancel | 放弃对应任务，等待执行者释放，持久登记取消处置；远端是否已提交按实际结果报告 |
| ClearHistory | 仅移除满足保留策略、原生关联已解除且文件清理已完成的终结任务；保留必要回执与来源处置 |

正常的状态竞争返回逐项确定结果，例如取消前已完成。普通任务失败不改写其他独立项；共同数据库故障结束依赖它的操作，未执行项不标成功。取消等待只停止 Wait，不撤销已受理的操作；不再使用面板 Token 管理持久任务寿命。

单项操作和批量操作走同一调度命令通道，消除必须暂停整个服务才能修改一个无关任务的限制。命令中仅持久保存意图，等待原生资源释放时不得阻塞整个仓库写队列。

### 5.5 清理与空间策略

| 对象 | 默认策略 | 不能删除的条件 |
| --- | --- | --- |
| 空闲缩略图 | 32 MiB 内存预算，LRU | 仍有使用租约 |
| 已完成 / 取消的上传文件 | 记录清理意图后及时释放 | 原生或托管执行者尚未释放；提交归属不明确 |
| 暂停 / 失败 / 待上传文件 | 保留，等待恢复或显式取消 | 仍是任务恢复所需的唯一副本 |
| 已完成 / 取消任务历史 | 建议保留 30 天，数量上限 10,000 条；满足任一淘汰条件即可成为候选 | 服务器结果未确定、执行代次尚未释放、清理未完成、必要回执缺失或仍有实际执行 / 对账依赖 |
| 已结束批量操作的逐项结果 | 与任务历史采用相同保留窗口，按页清理；保留最小操作头 | 仍有待执行项、未释放资源或活动等待依赖 |
| 失败 / 需关注任务 | 不随成功历史自动清除 | 尚未被显式处理 |
| 未提交准备文件 | 仓库恢复后依据操作与文件归属清理 | 仍有有效准备操作或原生写入者 |
| 备份回执、排除基线、取消处置 | 保留判断所需的最小记录 | 仍有有效自动备份范围或恢复依赖 |
| 服务端未完成上传会话 | 显式启用后按最近活动时间过期，建议初始值 7 天 | 正在传输 / 校验 / 提交，或已生成确认备份 |

清理按页选择候选，执行时重新检查版本及引用。预览结果不是删除授权的永久快照；执行前状态变了就跳过并报告原因。每轮限制项数和时间片，避免整库长事务或大量文件删除阻塞界面。

提供可回收、在用、失败待处理、数据库 / WAL、上传文件和缩略图的独立统计。模块逻辑暂存预算与文件系统可用空间分别检查；空间不足停止继续准备新文件，不能自动删除未备份文件。数据库维护也需要空间，不等磁盘完全耗尽才触发清理。

清理成功返回实际删除项和实际释放文件字节；数据库逻辑删行不能直接算作同等文件空间释放。一次清理失败保存错误，由显式 RetryCleanup 重试；异常退出时尚未完成、尚未记录失败的清理意图可继续恢复。

逐项结果过期后，查询返回持久操作头并明确标记明细已过期；相同 OperationId 仍不能重新执行。未知 ID 返回不存在，不能与结果已过期混淆。备份回执和来源处置独立保留。服务器结果未知的任务先通过既有身份核对，失败则保留需处理状态和原因；保留窗口不将未知结果直接当成取消。

服务器会话清理使用与上传 / 提交相同的互斥规则：事务认领过期会话，阻止继续使用该会话，再清理分片并完成记录。中断后恢复同一清理意图。客户端恢复遇到会话已过期需得到明确错误，通过声明的重新建会话流程处理；不能伪装为上传成功。TTL 不适用于已完成备份及其他记录引用的共享文件。

本轮不承诺元数据磁盘永远恒定：备份事实可能随来源版本持续增长。主要目标是查询与内存有界，并通过明确的范围停用 / 重置操作管理不再需要的记录。

| BackupMaintenance.PreviewAsync(policy, token) | 分类占用与当前可清理候选摘要 |
| BackupMaintenance.RunAsync(policy, token) | 实际清理结果；删除前重新验证候选资格 |

接口收敛：汇总只读取持久计数与队列暂停，不混入瞬时系统网络状态；容量统计和逐任务等待原因分别由维护、任务页提供。任务变化使用 ReadChangesAsync 游标读取，图库 Watch 提供生命周期订阅。

任务变化通知与图库通知共用“有序变化批次 + 过期后刷新”的消费方式，不共用图片处理队列。UI 订阅由面板作用域释放，持久仓库和原生传输由应用服务拥有。

ImageBackupService.CreateAsync 继续作为业务启动入口；上传协议与服务器认证不因 SQLite 化改变。GetTasks 的全量调用点替换为分页 / 汇总，现有示例、测试窗口和测试一起改；本轮不增加全量接口兼容适配器。

## 7. 实施阶段与合并条件

执行顺序为 L0 → L1 → L2 → L3 → L4 → L5 → L6 → L7。每阶段可以形成独立可审查提交；后续阶段不掩盖前一阶段未通过的检查。中间阶段使用全新的测试仓库，不在用户运行时添加多格式识别分支。

通用 Sqlite 的 S0–S2 提供绑定、连接 / 事务和生命周期能力，是 L1 仓库接入的前置条件；L0 可以先完成业务 schema 设计。数据库快照属于通用模块 S3，照片上传不依赖该能力，不为它阻塞已通过基础验收的业务接入。

| 阶段 | 具体工作与交付物 | 完成门槛 |
| --- | --- | --- |
| L0：接入与契约 | 复用 Sqlite S0 的共享核心；固定 library / catalog schema、统一原生 BackupRepository、目录定位和代次协议；建立 1万 / 10万任务基准 | 三端共用核心与仓库测试向量；没有 Unity 时能定位并打开既有任务库；所有权和中断窗口可逐项验证 |
| L1：持久化替换 | 实现共享原生 BackupRepository；平台仅保留系统适配；替换任务、配置、基线、回执 JSON；实现准备和清理意图恢复 | 上传 / 下载 / 暂停 / 取消回归通过；后台完成一次提交即为业务事实；无旧 JSON、双写或重复任务状态机 |
| L2：按需查询 | 去掉全量内存字典、全量 GetTasks；任务分页 / 汇总 / 变化记录；自动扫描逐页批量判重；下载基于独立回执 | 10万历史启动及首屏不实例化全量任务；已完成回执与下载不依赖任务历史；实际查询使用预期索引 |
| L3：图库索引与变化 | 实现带身份 / 代次的游标、完整核对和基线激活；接入 PhotoKit / MediaStore；目录按能力核对；优化原生元数据交付 | 增删改、相册移出、日志截断、重启和权限变化通过；中断枚举不提交缺失删除；大基线无全量提交事务 |
| L4：共享缩略图 | 统一来源 / 纹理租约、请求及字节预算、LRU、在途合并、单等待者取消和版本失效；虚拟列表接入 | 相同键并发只处理一次；相同键取消后可重新申请；大量排队有界；长时间滚动后无泄漏和串图 |
| L5：批量任务中心 | Selecting / Running 阶段、分批目标构建、逐项结果、全局 / 单项暂停关系、分页 UI 与汇总 | 筛选语义明确；无一次全库写事务；历史清理不丢操作结果；重开能恢复未失败阶段；旧代次不能覆盖重试后的任务 |
| L6：清理与容量 | 历史保留、文件清理预览 / 执行、空间统计、数据库维护、本机服务器过期会话回收 | 不删除在用或恢复必需文件；清历史后不重复备份；清理和提交竞争测试通过 |
| L7：发布验证 | 更新使用文档、构建处理器、示例；Android / iOS 真机与压力 / 长时测试 | 构建、功能、错误恢复、性能记录齐全；明确未支持平台与系统限制 |

L0 若受设备或构建依赖限制，记录具体阻塞项；可以完成独立的 schema 和桌面验证，但不能把移动端存储接入标成已完成。不得以语法编译替代 IL2CPP 链接与真机读写验证。

## 9. 验收矩阵

### 9.1 正确性与故障

| 编号 | 场景 | 必须验证 |
| --- | --- | --- |
| C01 | 首次建库、重开、不同账号、损坏 / 非预期 schema | 身份校验明确失败；不导入旧 JSON、不自动删库 |
| C02 | 在每个接收 / 交接 / 完成 / 清理窗口中断，大请求分批接收 | 单个受预算约束的批次不交付半批成功；不同批次状态分别可查；不重复执行同代次，不提前删文件 |
| C03 | 数据库满、文件满、锁等待超时、提交失败 | 不发布未提交成功；原异常及已确定状态保留；独立资源尽力释放 |
| C04 | 单 / 全等待者取消、同键立即重申请、缓存关闭、首个调用方释放来源 | 所有等待有终态；来源由在途项持有；旧完成不伤新项；仍被使用的纹理有效；无重复 Destroy |

| C07 | 部分授权扩展 / 缩小、相册移出、目录授权撤销 | 可见范围变化与删除分离；不删除服务器副本；相关任务按策略停止 |
