# 商业游戏 SQLite 存储架构与实施计划

日期：2026-09-30  
状态：实施中。通用核心、托管接口、维护与快照已有代码及桌面验证；移动端和商业发布门槛尚未通过。当前实现与证据见 [Validation.md](Validation.md)。本文替代此前分别选择 C#、Android 和 iOS 数据库封装的方案。  
位置：Packages/UIFrame/Runtime/Sqlite。

面向长期运营的商业游戏。以数据可靠性、明确的资源所有权、可测量的帧耗时和内存、跨平台一致行为及可维护的构建链作为交付标准。通用模块遵守 [ErrorContract.md](../../Docs/ErrorContract.md)，照片业务另见 [照片备份计划](../../Docs/GalleryLongTermBackupPlan.md)。

## 1. 固定决策

| 决策 | 本轮方案 |
| --- | --- |
| 数据库引擎 | 使用 SQLite 官方源码，锁定版本、源码校验值、编译配置；不自研引擎 |
| 跨平台执行层 | 一份 C/C++ 存储核心；各目标编译，行为一致 |
| 对外边界 | 稳定 C ABI；C# 为类型化异步门面；平台桥接只做必要适配 |
| 写入权 | 同一数据库由一个核心上下文管理，一个写入连接；业务仓库是业务状态的唯一写入入口 |
| 读写并发 | 写入串行；按固定预算使用一个独立只读连接，提供短查询，不开放无界连接池 |
| 线程 | SQLite 执行、事务和快照由原生核心的有界调度器管理；托管层不再建立另一套 SQL 调度器 |
| 持久化 | WAL + synchronous=FULL 作为可写持久库基线，提交后才确认保存成功 |
| 游戏使用方式 | 内存运行态 + 显式持久化边界；不在每帧逐实体查询数据库 |
| 业务隔离 | 通用模块不含游戏或照片表；游戏仓库由 C# 实现，需脱离 Unity 运行的备份仓库使用共享原生实现 |
| 数据格式 | 首版只有当前 schema；不增加旧 JSON 识别、迁移、双写或运行时备用后端 |

一致性与可靠性优先于吞吐数字。通过批量事务、索引、减少跨语言调用和有界异步执行提升性能，不使用关闭同步落盘、吞错或“先报成功后写盘”的方式提升指标。

本文的移动端预算和性能数字仍是待真机校准的目标。桌面实现与基准不代表已达到商业发布质量；阶段勾选按完整门槛完成，不按代码存在与否完成。

职责分配：

- Runtime/Sqlite：引擎、ABI、连接、命令执行、事务、取消、查询结果、快照、诊断和平台构建。
- 游戏仓库：存档槽位、背包、任务、业务 schema、索引、幂等操作和存档时机。
- 图库仓库：照片元数据、授权范围、版本、扫描代次及增量发现。
- 共享原生备份仓库：备份任务、执行代次、确认回执和清理意图；在 Unity 未运行时也能提交系统传输结果。
- Android / iOS 适配：系统调度、权限、网络请求、系统任务关联及安全凭据存取，不各自实现备份 SQL 或状态转换。

Android、iOS 和 C# 使用本模块管理的数据时，都经过同一存储核心，不再分别选用 Android SQLiteDatabase、iOS 系统 sqlite3 和另一份托管绑定来实现同一业务。其他 SDK 可以使用自己的数据库；不能用它们的连接打开本模块拥有的文件。

按业务划分文件，例如 game-save.sqlite、library.sqlite 和每个账号的 catalog.sqlite；不按语言复制数据。共享库不意味着所有业务共用一个文件，更不意味着每个模块各维护一份相同任务状态。

## 4. 引擎与 ABI

### 4.1 构建基线

S0 已锁定官方 SQLite 3.53.4、源码ID及哈希；源码校验值见 Native~/third_party/sqlite/source-lock.json，工具链配置和产物哈希见各平台 Plugins 构建清单。当前 C ABI 为3，不在客户端运行时下载依赖。移动端运行验收仍未完成。

- SQLite 开启线程安全配置；同一连接仍只由一个执行任务持有，不能依赖引擎锁代替业务所有权。
- 关闭运行时扩展加载；按实际使用固定 SQL 功能集合，并覆盖编译选项差异测试。
- 隔离 SQLite 符号，统一导出带模块前缀的 C ABI。特别验证 iOS 静态链接和其他插件的 SQLite 共存，不意外绑定到系统或另一插件的引擎。
- 进程中的本模块只加载一份引擎实例；照片仓库链接到它，不再次静态嵌入 SQLite。实际加载版本、源码标识和编译选项可诊断。
- Android、iOS、macOS Editor、Windows 按交付目标构建。Android 实际 ABI 和最低 API 沿用宿主要求，不为接入存储擅自提高或缩减。
- 验证 IL2CPP、裁剪、Android 混淆、iOS 符号和链接、Editor 原生库导入。公开 ABI 不依赖托管反射或动态生成代码。

### 4.2 互操作规则

- 只跨 ABI 传递固定宽度数值、明确编码与长度的 UTF-8 数据、带代次的句柄和有界结果缓冲；不导出 C++ 容器或异常。
- 每个结构包含 ABI 版本 / 大小。托管与原生产物不匹配时在打开前明确失败。
- 原生创建的缓冲由原生释放；每个句柄只有一个所有者。释放后使用、重复释放和旧代次访问有确定错误。
- C# 一次提交一个参数化命令或批次，原生一次返回结果页；不逐列 P/Invoke，不让 Android 逐行 JNI，也不通过 JSON 编解码每个数据库值。
- C# 门面负责参数快照、任务完成和结果映射；原生核心负责实际调度与资源生命周期。
- 完成分发采用可唤醒等待和批量领取结果，不依赖 Unity Update，也不每帧忙轮询。不按每条 SQL 创建线程。
- 不从数据库事务中反向调用 C# / Java 业务委托。映射在短查询结束后执行，映射失败不能回滚早已提交的写入。

## 5. 调度、事务与数据所有权

### 5.1 连接与线程

一个可写数据库上下文持有一个写入连接和最多一个只读查询连接；独立只读数据库只建立只读连接。工作由固定大小的原生线程池执行。每个连接同一时刻只执行一个任务；同库写命令按受理顺序执行，不同库可以在工作池容量内独立推进。

调度器为写入保留执行机会，查询与维护不能长期占满全部工作槽位。长维护按步骤让出工作线程；明确记录各类队列的最长等待和公平性，不在数据库工作线程上同步等待另一个排队命令。

保留执行机会是调度规则，不是实时完成保证：已经开始的原子事务、刷盘和不可中断 I/O 不能被另一请求抢占。限制单事务 SQL 数不能限制一条 SQL 影响的行数；大范围 INSERT / UPDATE / DELETE 由业务按稳定键分批执行，单批行数和耗时一并测量。网络准备、结果映射及业务委托不占原生数据库工作槽位。

只读连接开启只读限制，只执行只读语句。查询结束即释放语句与读取快照，不允许界面跨帧持有 SQLite 游标或长读事务。没有查询需求时可延迟建立读连接。

读操作看到其开始时的已提交快照。调用方等待写入成功后再发起查询，应能读到该提交；并发中已开始的查询可以看到此前快照。跨多页不承诺冻结视图，稳定分页由业务查询上界和版本定义。

长扫描、清理和导入拆为有界业务批次，每批提交后让出调度机会；不能切开调用方声明为原子的事务。原子事务超出预算时明确失败，由业务重新设计其原子边界。

OpenAsync 明确区分 CreateNew、OpenExistingReadWrite 和 OpenExistingReadOnly。新建不能覆盖已有文件，打开不能悄悄生成空库；只读模式不执行需要写入的 WAL 配置。新建失败仅清理本次新建且未移交的文件，既有库打开失败不能删除数据。

上下文注册和文件锁由核心统一管理，防止 C# 与原生通过两个入口重复取得同文件的写入所有权。默认后台适配运行在应用同一进程；独立 Android 进程不在首版支持范围，未设计跨进程命令所有权前不能启用。

首次登记同时校验规范化路径与已打开文件的身份，不能只用原始路径字符串去重。数据库打开期间不允许外部替换或重命名该文件；恢复也须先释放相同文件的全部上下文。

### 5.2 批量事务

事务 API 提交不可变 SqliteBatch，包含有序 SQL、参数、结果上限和必要的受影响行数条件。核心在一个事务内执行，任何 SQL、条件或结果预算检查失败都回滚。

核心只提供执行顺序、SQL 和行数条件等最小原语，不发展为脚本语言、业务规则引擎或 ORM。事务内动态关系由 SQL 和业务仓库表达，不能在持有事务时等待网络或托管回调。

外部 SQL 入口不能自行 BEGIN / COMMIT、附加其他数据库或改写核心管理的连接配置；使用 SQLite 的授权与语句信息校验边界，不靠字符串前缀猜测 SQL。业务建表及索引通过受控批次执行。此限制保护事务、文件归属与连接配置，内部事务执行器负责相应合法操作。

共享原生业务仓库可以使用核心的受控内部事务 Session；它与 SqliteBatch 使用同一个事务执行器、配额、行数条件和取消 / 提交状态机，不是第二套事务实现。Session 只在核心执行任务期间有效，不直接绕过核心打开 sqlite3 连接；会话内执行的语句同样计入预算。

事务结果在 COMMIT 成功后交付。可写批次的必要结果内存应在提交前完成预算预留和构造，避免先提交再进行不受控结果分配。跨语言交付仍可能被进程退出打断，业务通过 OperationId 和事务内回执判断是否已经提交。

### 5.3 初始资源预算

以下为候选默认值，S0 / S4 按真机测量锁定；调整必须说明保护对象、失败行为和吞吐代价。

| 项目 | 初始预算 | 超限行为 |
| --- | --- | --- |
| 原生执行线程池 | 全模块 2 个工作线程 | 在有界队列中等待；不自动扩展线程 |
| 每个可写库常驻连接 | 1 写 + 最多 1 只读 | 不自动扩展常驻连接池 |
| 全模块快照槽位 | 同时 1 个；独立来源只读连接 + 临时目标连接 | 仅在显式快照期间持有，计入维护预算；槽位占用时明确报告忙碌 |
| 每库待执行命令 | 128 项，同时限制参数缓冲合计 4 MiB | 受理前报告 QueueCapacityExceeded；不静默丢弃 |
| 已预留 / 持有的结果 | 每库 4 MiB，并受全模块缓冲预算约束 | 执行前预留；排队、执行、未领取及已移交未释放的结果共享额度 |
| 全模块自有参数 / 结果缓冲 | 合计 16 MiB | 受理前进行配额控制；不影响已提交结果的交付 |
| 查询结果页 | 默认最多 200 行 / 1 MiB 编码数据 | 超过任一上限明确失败，不截断为成功 |
| 单事务 SQL 数 | 初始最多 200 条 | 拒绝过大原子批次；不把该值当成影响行数或运行时间上限 |
| 预编译语句缓存 | 每连接最多 64 条，并设内存目标 | 淘汰空闲语句；过大语句正常执行但不保留缓存 |
| SQLite 页缓存 | 每连接建议 4 MiB | 这是引擎配置目标，不是进程内存硬上限 |
| 查询 / 命令截止时间 | 默认 5 s，按操作显式配置 | 中止所属操作并按事务语义结束 |
| 锁等待期限 | 默认 100 ms，受操作剩余时间约束 | 报告锁错误，不重放写入 |

准入先校验 SQL、参数数量、单值长度与编码长度，进行防溢出计算及配额预留，然后复制不可变参数；不能先复制巨型 BLOB / 字符串再检查队列预算。托管编码与原生接收的临时双份缓冲都计入模块占用，不能仅统计最终原生副本。S0 固定相应 sqlite3_limit 配置，限制单值、SQL 长度及参数数量；这些限制仍不是所有引擎临时内存的硬上限。

每个命令在受理时预留参数、声明的最大结果额度和终态记录；结果物理内存可逐步分配，但须在写事务 COMMIT 前构造完成。额度不足在执行前拒绝，不能持有连接 / 事务等待客户端领取结果。成功、失败及取消的终态通知不依赖剩余的数据结果配额；无人领取时仍能结束操作及 CloseAsync。配额是各项同时生效的上限，不保证 128 个最大结果请求都能同时受理。

缓冲预算覆盖排队、执行、未领取与已移交未释放的原生结果；释放句柄后才归还额度。QueryPageAsync 完成映射即释放原生页，返回的托管集合归调用方，不能依赖调用方是否 await 才释放原生资源。SqliteBatchResult 的资源由接收者显式释放，独立于连接寿命；泄漏占用可诊断，但不能通过关闭连接使已交付数据失效。

内存统计区分模块缓冲、托管物化、SQLite 页缓存 / 排序临时数据和线程栈。映射并发与待映射页同样受限，完成分发只交接结果，不执行任意业务委托或内联 Task 延续，避免一个慢映射阻塞其他操作的完成。调用方创建或长期持有的对象不在原生配额内；SQLite cache_size 也不是硬内存保证，不能将上述配置相加后宣称整个进程一定不超过该值。

语句缓存按 SQL 和连接区分，归还时 reset / clear bindings，schema 变化后重新准备，不跨线程共享正在执行的语句。运行时不做全历史对象缓存，不在每次查询中创建全部实体后再分页。

## 6. 游戏运行态与持久化边界

游戏逻辑在内存中运行，数据库用于明确的保存点与持久事实。UI 和战斗循环不直接访问数据库。

| 数据类型 | 业务策略 |
| --- | --- |
| 角色位置、可合并的普通设置 | 允许合并尚未提交的最新快照；“已排队”与“已保存”状态分开 |
| 离线进度、存档槽位 | 在检查点形成不可变快照，事务提交后才标记保存完成 |
| 背包扣减与获得、任务领取 | 业务相关变更和 OperationId 回执在同一事务内提交 |
| 联网经济、付费权益 | 以服务器确认为权威；SQLite 保存本地缓存和待处理记录 |
| 离线上行操作 | 业务数据与待发送记录同事务保存；服务器按 OperationId 幂等处理 |
| 静态大配置 | 可以使用独立只读数据库；小配置不强制迁入 SQLite |

本地 SQLite 不能承担防作弊或服务器权威验证。加密或哈希也不能使客户端成为可信的经济账本。

例如一次允许离线执行的道具兑换，应在同一事务内检查余额 / 数据版本、扣减材料、增加物品并记录 OperationId；任一条件不成立则不提交。网络发送在事务之外进行，不能把 HTTP 请求包含在数据库事务中。

合并写入只适用于业务明确允许覆盖的快照；交易、奖励和待发送操作不能使用“只保留最后一条”策略。保存失败必须保留可观察的未保存状态，不能在退出回调中临时尝试后就宣称可靠存档。

## 7. 错误、取消与关闭

| 情况 | 契约 |
| --- | --- |
| 排队前 / 排队中主动取消 | 没有执行 SQL，取消所属等待并释放参数 |
| 执行中主动取消 | 核心按操作 ID / 代次中断，回滚未提交事务；解除中断关联后才运行下一操作 |
| COMMIT 后取消 | 返回已确定提交结果，不能宣称未写入 |
| 约束、SQL 或业务行数条件失败 | 只结束该事务；回滚成功、连接状态可信时其他独立事务继续 |
| 查询映射错误 | 查询失败且资源释放；不改变已提交业务数据 |
| 回滚失败、提交结果不明、连接损坏 | 停止依赖该上下文的新工作；结束受影响等待，仍允许诊断和关闭 |
| 其他库正常 | 不因共享线程池或 provider 而一并封锁 |
| 系统锁屏暂时无法访问数据 | 报告实际访问状态；不能当成损坏并重建 |

原生错误返回稳定类别、SQLite 主码 / 扩展码、操作 ID、阶段及是否已确定提交；跨 ABI 不传播 C++ 异常。内部已有异常保留身份和堆栈，次级释放错误单独记录。锁超时、磁盘满及 SQL 失败均不自动重试。

取消不能仅按 SQLITE_INTERRUPT 判断：必须确认是当前操作的取消请求。进度处理器和取消注册在放行下一操作前解除，旧 Token 不能误伤后续命令。

截止时间约束排队与可中断执行；不能保证立即中止底层文件系统的不可取消 I/O。连接须等原生操作真实结束后才复用，并据实际提交结果完成等待，不能超时后先释放连接再让迟到写入继续发生。

CloseAsync 停止该所有者受理新工作，已受理操作按其截止时间和取消状态结束，最后释放连接；关闭不提供“中途放弃释放”。重复关闭等待同一最终结果，不重新尝试此前失败的清理。

Editor 域重载、退出播放模式和托管门面关闭必须使用同一客户端注销协议：先停止受理，结束该客户端已接受的等待并释放未移交结果，再注销带代次的完成接收端，等待在途回调离开后释放托管引用。原生层不能持有已卸载域的委托或 GCHandle；关闭期间完成分发仍须可用，不能先停完成泵再等待任务结束。域重载不卸载仍被应用后台服务持有的核心，也不把旧客户端结果交给新客户端。S0 必须验证域重载开启和关闭两种配置。

通用数据库所有者关闭与 C# 备份门面释放是不同操作。原生备份仓库的生命周期属于应用后台服务，C# UI 关闭不能关闭其数据库或取消已接收传输。先关闭任务受理、明确暂停 / 取消并等待释放，才能进行业务仓库的最终关闭。

## 8. WAL、磁盘与快照

### 8.1 日常维护

按 WAL 页数、空闲机会和磁盘水位执行受控 checkpoint，先使用非阻塞维护；没有完成回收要报告仍被读快照占用的情况，不阻塞主线程强行清空。写事务内不执行 checkpoint 或 VACUUM。

只读查询有截止时间且及时结束，防止长读无限拖延 WAL 回收。超过配置的磁盘高水位时停止受理需要继续增长的工作并报告原因；完成已有工作所需空间必须计入预留。水位是准入策略，物理磁盘满仍须通过真实错误路径处理。

删除业务行不会立即释放同等文件字节。数据库压缩由维护窗口显式安排，计算额外磁盘需求，不在每次清理后 VACUUM。持久数据库、WAL / SHM 与临时文件遵循平台目录和文件保护规则。

### 8.2 一致性数据库快照

使用 SQLite Backup API。需要在写入继续进行时制作快照，应由受控读取快照连接固定来源版本，在有界步骤中生成独立临时目标；不复制正在写入的主数据库文件。

快照使用全模块唯一的维护槽位，为源库临时打开一个专用只读连接及一个临时目标连接，结束后关闭；不占用前台查询连接，也不形成可扩展连接池。两端页缓存、结果和临时磁盘占用独立记账，准入失败时不先打开额外连接。快照来源仍受原数据库上下文的所有权约束。

首次读取确定来源版本后才开始复制；各步让出工作线程但保留该读取快照，不能通过每步释放读取事务来改变快照含义。快照步骤与其他维护在工作池中最多占一个执行槽位，写入和短查询可在剩余容量推进；不承诺消除设备层面的 I/O 竞争。来源上下文关闭时先结束快照，不能留存失去所有者的读锁。

快照持有读取版本会延缓 WAL 回收，因此同时设置时间、磁盘增长和临时文件预算。超限明确取消 / 失败并释放快照，不能无限等待。业务选择空闲或安全存档窗口，以减少干扰关键写入。

成功必须完成 backup_finish、关闭目标、必要的完整性校验和刷盘，并通过同文件系统内的发布步骤交付完整目标。目标必须可独立打开，不依赖未交付的 WAL / SHM；既有目标不被覆盖。

快照失败仅清理本次临时文件。恢复在目标仓库停止后由业务核对数据库身份、schema 和外部文件依赖，保留恢复前状态，并通过明确的替换流程完成。此处不提供运行中直接覆盖数据库的入口。

数据库快照只覆盖一个数据库。照片原文件、资源包、其他数据库和云端提交不在同一 SQLite 事务或快照中；完整备份由业务定义清单与发布点。

## 9. schema、版本与运营

通用插件只识别引擎与 ABI，业务仓库定义 application_id / schema 版本及建表 SQL。首版只支持实际存在的当前 schema，不添加旧 JSON 扫描、兼容、导入或双写。

商业发布后出现真实 schema 变更时，随业务版本提交显式升级步骤、事务边界和已发布版本测试样本。该工作针对未来真实存在的 SQLite 数据，不能预先编写猜测的历史格式兼容器。

发布检查必须同时考虑客户端回退：较旧客户端遇到较新 schema 应明确拒绝写入，不能猜测降级、删除重建或覆盖玩家数据。升级前快照、失败恢复与是否允许版本回退由具体业务发布方案决定。

当前实现按需提供累计诊断，不自动生成成功日志或诊断文件。项目接入遥测时记录模板 ID、耗时、行数、字节数、队列等待、事务结果及匿名仓库标识，不记录 SQL 参数、令牌、照片路径或玩家私人内容；高频成功事件需要采样。此处的遥测接入属于项目发布验收。

插件提供以下低成本统计：队列长度 / 字节、等待与执行延迟、事务提交耗时、语句缓存命中率、结果缓冲占用、SQLite 内存、WAL 大小 / checkpoint 进度、超时 / 取消 / 错误数。业务层另外记录保存失败、待同步数和需要玩家处理的状态。

## 10. 拟定托管接口

以下主要接口已实现；完整重载与统计字段见 README 和源代码，阶段验收状态另列：

~~~csharp
Task<SqliteDatabase> OpenAsync(
    SqliteOpenOptions options, CancellationToken token = default);

Task<int> ExecuteAsync(
    SqliteCommand command, CancellationToken token = default);

Task<IReadOnlyList<T>> QueryPageAsync<T>(
    SqliteCommand command, SqliteQueryBudget budget,
    Func<SqliteRow, T> map, CancellationToken token = default);

Task<SqliteBatchResult> ExecuteTransactionAsync(
    SqliteBatch batch, CancellationToken token = default);

Task CreateSnapshotAsync(
    SqliteSnapshotOptions options, CancellationToken token = default);

SqliteDiagnostics GetDiagnostics();
Task CloseAsync();
~~~

OpenAsync 为静态工厂，其余为实例入口。查询映射在受限的托管工作项中处理有界原生结果，不占用 SQLite 工作线程 / 连接、不访问 Unity 对象；SqliteRow 只在本次映射期间有效。QueryPageAsync 为只读查询，超过预算报错；不隐式为任意 SQL 添加 LIMIT。业务提供有索引的分页 SQL，行数预算不能代替正确的查询计划。

ExecuteAsync 仅用于无结果集的单条命令；带返回行的写入通过事务批次返回 SqliteBatchResult，不能忽略返回数据假装只是受影响行数。

SqliteBatch 在受理前固定 SQL、参数和行数条件。SqliteBatchResult 拥有有界结果资源，使用方必须释放；托管门面在失败路径释放尚未移交的原生缓冲。结果数据的具体布局、零值 / NULL 和数值溢出规则在 S0 冻结并跨平台测试。

核心不提供持有事务时执行任意托管委托的接口，也不暴露 sqlite3 裸连接。公开接口只承诺所属操作的数据库结果，不承诺自动重试、账号识别或跨库事务。

### 12.2 性能门槛

先在指定最低档位 Android / iOS 真机建立 Release / IL2CPP 基准，记录设备、温度、空闲磁盘、冷 / 热状态和负载。以下为初始目标，不能用 Editor 数字替代；变更目标须给出测量依据并记录为设计变更。

| 工作负载 | 初始目标 |
| --- | --- |
| 普通游戏请求的主线程提交与结果交付 | 不包含 SQL 执行；每帧合计 p95 ≤0.5 ms、p99 ≤1 ms；大结果分批交付 |
| 10万行有索引数据，每页100条、结果≤128 KiB | 无排队基准下端到端 p95 ≤20 ms、p99 ≤50 ms；另测负载下排队延迟 |

| 1万 → 100万历史，活跃请求量固定 | 打开和首屏不实例化全历史；业务托管常驻增量目标≤10 MiB；同时报告原生内存 |

| 10万项批量导入 / 清理 | 分批推进，对前台查询无无限饥饿；统计吞吐、帧耗时和最大队列等待 |

| 24小时稳定活跃负载 | 预热后无随执行轮次持续增长的托管对象、原生句柄、缓冲或数据库连接 |
